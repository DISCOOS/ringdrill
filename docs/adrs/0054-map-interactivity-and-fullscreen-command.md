# ADR-0054: Consistent map interactivity on medium/expanded windows, via a built-in `MapView.withFullscreen` command

## Context and problem statement

The coordinator screen's all-stations map (`CoordinatorScreen._buildExercisePositionMap`) is directly interactive at every window size — pan/zoom/tap gestures live, its own FAB commands (layer toggle, zoom, centre) — with an ad-hoc "expand" `MapCommand` wired through `topRightCommands` that opened a bigger interactive copy in a dialog (medium/expanded) or bottom sheet (compact). The Station and RolePlay mini-maps (`StationMiniMap`, `RoleMiniMap`), and the exercise-card preview (`ExerciseMiniMap`), instead rendered a static, `IgnorePointer`-wrapped preview at every window size: a single tap was required just to reach an interactive map, opened the same dialog-or-sheet way. Reported: this reads as inconsistent — the same kind of content (a map with markers) behaves two different ways depending on which screen shows it, and the coordinator's own "gold standard" approach was never extended to the other three.

A second, independent bug surfaced while tracing the ad-hoc expand button: it was passed with no explicit `size:`, so it resolved its FAB diameter via `MapCommandSize.of(context)` (full-window `MediaQuery`) — while every *internal* `MapView` command (the layer toggle included) resolves via a local `commandSize` derived from `MapView`'s own `LayoutBuilder` constraints. On any embedding narrower than the full window (a split pane, a narrower dialog) the two sources can disagree, rendering visibly mismatched button sizes in the same stack.

## Decision drivers

* One consistent map interaction model above the compact breakpoint, matching the pattern the user already preferred (the coordinator's own map) rather than inventing a fourth variant.
* The "go bigger" affordance should be a genuine full-screen route, not a dialog — dialogs cap width/height and read as "a form popped up," not "now looking at the map properly."
* The expand command's sizing must come from the same source every other built-in command already uses, closing the mismatch bug structurally rather than patching the one call site that happened to be reported.
* A directly-interactive embed needs real vertical room for its FAB stack — a list-tile-sized thumbnail (existing Station/RolePlay list rows use a fixed 140px preview) cannot fit a zoom+centre command column without overflowing, regardless of how wide the window is.

## Considered options

* **A: Add `MapView.withFullscreen`/`fullscreenHeader`; let each mini-map self-detect interactivity from its own local width *and* height via a `LayoutBuilder`; make the fullscreen push a real `MaterialPageRoute`.** Tried first, reverted — see the second "Bad" consequence below.
* **B: Keep the ad-hoc `topRightCommands` FAB pattern, just pass `size:` explicitly at each call site.** Rejected: fixes the reported mismatch but not the underlying pattern — every future caller wiring its own expand button would need to remember the same fix, and the "which surfaces are interactive" question would still be answered inconsistently per-file.
* **C: Make every mini-map interactive at every width, including compact.** Rejected: out of the confirmed scope for this pass (compact's existing tap-to-expand-sheet flow works and was not reported as a problem); revisit separately if compact needs the same treatment later.
* **D: Gate mini-map interactivity on local width alone, matching the coordinator's own map (which has no such gate).** Rejected during implementation: this shipped a real regression — Station/RolePlay's list-tile embeddings (`station_list_view.dart`, `roleplay_list_view.dart`, both a fixed 140px preview) are wide enough to read as medium/expanded but far too short for the FAB stack, producing a `RenderFlex overflowed` in a real widget test the moment this option was tried.
* **E: Add a caller-supplied `interactive` bool to each mini-map; let `StationPositionPanel`/`RolePositionPanel` forward their own existing `fillHeight` straight through, instead of the mini-map re-deriving an answer from its own constraints.** (chosen — see below.)

## Decision outcome

Chosen option: **E**, arrived at after A was implemented, shipped a real bug, and was replaced in the same pass.

**`MapView` gains two params.** `withFullscreen` (bool) shows one more command in the existing top-right column, right after the layer toggle, sized from the exact same local `commandSize` variable that command already uses — no second sizing source, so the mismatch bug cannot recur for this command. `fullscreenHeader` (nullable `PreferredSizeWidget`) is the `AppBar` shown only inside the pushed route; null renders a minimal `AppBar` with just `MasterDetailLeading`. Tapping the command pushes a `MaterialPageRoute` on the **root** navigator (mirroring `openFormSurface`'s push pattern) containing a fresh `MapView` clone — same markers, layers, cluster styles, search targets — with `withZoom`/`withCenter`/`withToggle`/`interactionFlags` force-set to fully interactive regardless of what the smaller embed itself opted into, since "fullscreen" always means fully interactive. No `controller:` is forwarded (the clone gets its own, so two simultaneously-mounted `MapView`s never fight over camera state), and no ambient-scope reprovisioning is needed the way `openFormSurface` needs it for live-resolving forms: `markers` are already-resolved `MapMarkerSpec`s with labels baked in as plain strings, and a marker's `onTap` closure keeps referencing whatever `BuildContext` built it originally, which stays mounted (just visually covered by the new route). Hero-tag collisions between the two simultaneously-mounted maps are already handled by an existing per-instance `UniqueKey()` (`_heroScope`, fixed earlier in this same map-work thread).

**`StationMiniMap`/`RoleMiniMap`/`ExerciseMiniMap` each gain an explicit, caller-supplied `interactive` bool** (default `false`, preserving today's static-preview behaviour for every existing caller that doesn't opt in), replacing a first attempt (Option A) that instead wrapped each widget's `build()` in a `LayoutBuilder` and self-detected via `WindowSizeClass.fromWidth(constraints.maxWidth) != compact && constraints.maxHeight >= MapConfig.minInteractiveHeight`. That self-detection shipped a real, confirmed bug: `WideDetailMapSplit` (the shared expanded-body split both Station's and RolePlay's detail screens use) caps its own left column at a flat 440px, so at a 900px expanded pane — comfortably past the screen's own 840px expanded threshold — the map pane itself is left only ~410px wide. Measured locally, that reads as `WindowSizeClass.compact`, so the mini-map fell back to the static preview even though the screen had already committed to its spacious, `fillHeight: true` layout. Confirmed by pumping the real `StationExerciseScreen` (not a hand-built reconstruction) at 900×800 in a test: zero FAB icons rendered under Option A's width check, all three under Option E. The caller (`StationPositionPanel`/`RolePositionPanel`, forwarding their own `fillHeight` straight through as `interactive: fillHeight`) already has the right answer — `fillHeight: true` is only ever passed once `_buildExpandedBody`/`_buildMapCard` (station_screen.dart) or the RolePlay equivalent has *already* decided this panel sits in an expanded pane. Re-deriving the same decision from the mini-map's own local constraints was strictly worse: those constraints don't tell the whole story once a sidebar of fixed width sits between the screen's own breakpoint and the map's actual render box. `MapConfig.minInteractiveHeight` (220px — the bottom-right zoom+centre column's own natural height, 188px of buttons plus 32px of padding) is kept as documented *guidance* for a caller deciding whether to pass `interactive: true`, not as an internally-enforced check. Each mini-map still factors its "interactive config" into one small private builder (e.g. `_interactiveStationMap`) shared between the interactive branch and the existing compact sheet's body, so the two configurations cannot drift apart.

**`openStationMapSheet`/`openRoleMapSheet`/`openExerciseMapSheet` become the "not interactive" fallback.** With interactivity now caller-decided, and the built-in fullscreen command handling "go bigger" via its own push once a caller does opt in, the `if (WindowSizeClass.of(context).hasMasterDetail) return showRingdrillDialogShell(...)` branch each of these three functions had is unreachable — deleted. Each keeps only its `showRingdrillActionSheet` (bottom sheet) branch, reachable only from a static preview (`interactive: false`, the default).

**`coordinator_screen.dart`'s ad-hoc expand FAB is replaced** with `withFullscreen: true, fullscreenHeader: ExerciseMapSheetHeader(exercise: ...)` on the same, already-interactive `MapView` it built before — no behaviour change to when this map is interactive (it always was, at every size, and never went through `ExerciseMiniMap`/the `interactive` flag at all), only to how "expand" is wired and where it goes.

### Consequences

* Good: exactly one map interaction model above the compact breakpoint — direct pan/zoom/tap plus a consistent-looking FAB stack, with the same "expand to fullscreen" affordance everywhere a caller opts in.
* Good: the button-size-mismatch bug is closed structurally, not patched at one call site — any future internal command built the same way (inside `_MapViewState.build()`, sized from the local `commandSize`) is immune by construction; a caller-supplied `topRightCommands` widget could still reintroduce a similar mismatch if it skips `size:`, which remains a caller responsibility outside this ADR's scope.
* Good: the "is this embed interactive" decision lives in exactly one place per screen (`_buildMapCard`/`_buildPositionPanel`'s `fillHeight` argument), not re-derived from possibly-misleading local render constraints — closing this ADR's own mid-flight regression (Option A) and, per the pattern, any future composition that similarly nests a map pane behind a fixed-width sidebar.
* Bad: `ExerciseMiniMap`'s only current real caller (`program_view.dart`'s exercise card) never passes `interactive: true` — it stays a static preview today even though this ADR's infrastructure supports making it interactive on request. Wiring that up was out of scope; a future pass can pass `interactive: true` there directly if wanted.
* Bad: compact windows keep three independent `showRingdrillActionSheet` call sites (one per domain) rather than folding into `MapView` itself — deliberately out of scope (see Option C), so this ADR does not fully unify the compact path the way it unifies the interactive one.
