# ADR-0053: `MapView` owns its default camera fit, centring and marker construction

*(Drafted in several passes across one continuous session of live-device testing on the same feature, initially as three separate ADRs. Merged into this one before anything was committed: they were one decision arrived at incrementally, not several independent decisions — later fixes found testing the same code are added here rather than filed as new ones.)*

## Context and problem statement

ADR-0051 consolidated every map surface's centering logic behind `MapConfig.fitFor`, but every caller still computed the resulting `CameraFit` *before* the `MapView` widget existed, using only a coarse `WindowSizeClass` guess derived from the *full window* (`MediaQuery.sizeOf(context)`). On a narrow phone, or inside a modal sheet/dialog with much less height than a full screen, flutter_map's own fit algorithm (`scale = (containerSize - padding) / boundsSize`) makes flat-pixel padding consume a much larger *fraction* of that smaller real viewport than the guess assumed — a fit for two markers ~100km apart could render a "250 km" scale bar on a narrow screen while correctly showing a tight "1 km" bar on a wide one, purely because the padding-to-viewport ratio differs, not because the geometry does. A second bug: several call sites render inside a dialog/sheet capped narrower than the full window, yet their `WindowSizeClass.of(context)` guess reads the full window and can report `expanded` when the map itself renders at `medium`-or-narrower width.

Fixing that (making `MapView` compute its own fit from its real render size) surfaced a second, independent problem once tested live on-device: flutter_map's own `CameraFit.bounds`/`CameraFit.coordinates` derive the camera's rendered *centre* from the same asymmetric `EdgeInsets` padding used to derive *zoom* — `projectedCenter = boundsCenter + (paddingBottomRight - paddingTopLeft) / 2`. Any one-sided padding source — most persistently the bottom-right FAB command column, which has no equivalent reserve on top — biases the centre away from the true marker centroid. Balancing individual padding *components* (tried first, for the label-footprint term) never fully fixed this, because the bias is structural to flutter_map's fit classes, not a tuning problem. A related report: a tight cluster of markers zoomed in only as far as the bare spread required ("50 m" scale, no surrounding context) rather than leaving room to see the surrounding area.

A third problem surfaced testing the same fix on real data: `MapMarkerSpec` construction for the three marker kinds the app plots (a station's own position, a scenario `Location`, a role/roleplay) had been reimplemented independently at 8+ call sites across several files, each written during a different pass of this same work. The drift this produced was real: two of four station-position-marker sites set `label` to the station's bare name while the other two correctly used *number + name* — the same station's pin showing different information depending only on which screen rendered it.

## Decision drivers

* Only `MapView` itself has access to its real, laid-out render size (via the `LayoutBuilder` its own `build()` already wraps everything in) — external callers computing a fit before the widget exists structurally cannot know this.
* The padding-driven centre bias is architectural — no amount of rebalancing individual padding components fixes it, because the bias comes from flutter_map's `CameraFit` implementations coupling zoom-driving padding to centre-driving padding. `centroidFit` already computes the exact intended centre (the true centroid) before ever calling into flutter_map's fit classes — it does not need flutter_map to *derive* one at all, only a zoom.
* Every station-position marker needs the same label/shortLabel policy; every scenario-location marker needs the same shape. This is data, not a per-screen UI choice, so it belongs in one place regardless of how many screens plot it — the same principle already driving `MapConfig.fitFor`'s consolidation, just applied one layer down (marker data, not camera math).

## Considered options

* **A: `MapView` computes its own default fit, centres via a small custom `CameraFit` that never reads padding for position, and every marker producer calls three shared builders instead of reimplementing construction.** (chosen — see Decision outcome for the parts)
* **B: Thread a real `Size` estimate through every external caller**, instead of letting `MapView` compute its own fit. Rejected: still requires each caller to know its own future render size ahead of layout, which several structurally cannot (a dialog/sheet's content height depends on its own children).
* **C: Fix the centring bias by mirroring every asymmetric padding source onto its opposite side** (as already done for the label-footprint term), instead of decoupling centring from padding. Rejected: the FAB command stack cannot be mirrored without wasting the exact screen space its own presence was meant to avoid wasting; would need re-deriving for every future asymmetric padding source instead of fixing the coupling once.
* **D: Leave marker construction distributed and just fix the inconsistent `label` values in place**, instead of consolidating into shared builders. Rejected: leaves the same drift risk for the next map surface someone adds — the bug was a direct, mechanical consequence of the duplication, not a one-off typo.

## Decision outcome

Chosen option: **A**, in three parts.

**Self-computed default fit.** `MapConfig.fitPadding`/`fitFor` change from a `WindowSizeClass sizeClass` parameter to a `required Size viewport`, deriving the size-class tier internally via `WindowSizeClass.fromWidth(viewport.width)`. The "aesthetic" flat-padding components (the 64px side floor, the flat 48px top/bottom bases used when there's nothing to clear) are capped against the real viewport size — never below half their flat value — while always-visible overlay chrome (FAB command stack, search field) stays unscaled, since it occludes markers for real if under-reserved. The marker-label footprint gets its own cap (15% of the viewport per axis, a plain `min`) since it is real space but *zoom-gated* — invisible below `MapConfig.labelMinZoomFor`, and an overview fit always lands below that zoom, so reserving its full flat width was zooming out to protect text drawn at opacity 0. `_MapViewState` gains `_lastConstraints`/`_knownViewport`/`_effectiveViewport` and `_defaultFitFor(context, markers)`, used as `widget.initialFit ?? _defaultFitFor(...)`. `didUpdateWidget` re-fits only when the actual `LatLng` point set changed, not on every rebuild handing `MapView` a new-but-identical `markers` list instance. Seven external call sites stop precomputing a fit they could never get exactly right anyway.

**Unbiased centring, zoom cap.** A small custom `CameraFit` (`_UnbiasedBoundsFit` in `latlng_utils.dart`) mirrors `FitBounds._getBoundsZoom`'s non-rotated zoom derivation exactly (so real overlay clearance still forces correct zoom-out) but always centres via `camera.withPosition(center: center, ...)` on a caller-supplied point — never a padding-offset projection. `centroidFit` returns this, passing its own already-computed centroid. Only the non-rotated case is implemented: this app never enables `InteractiveFlag.rotate`, so `MapCamera.rotation` is always 0 in practice. Separately, `MapConfig.fitFor` gained a `maxZoom` parameter defaulting to `MapConfig.defaultAutoFitMaxZoom = 16.5` — calibrated against flutter_map's own `Scalebar` bucketing, sitting at the top of the "100 m" reading — applied uniformly unless a caller passes `maxZoom: null`. `MapView`'s single/zero-marker fallback zoom (`_effectiveMaxZoom`, since renamed and generalised — see the seventh pass below) uses the same constant, replacing an earlier `labelDetailZoomFor`-based choice that answered an unrelated question (when a multi-marker fit's label can expand from a number chip to full text) and had zoomed a lone marker in as tight as a "25 m" reading for no reason.

**Consolidated marker construction.** `stationNumbering(exercise, station)` (in `station_mini_map.dart`) is now the one place that computes a station's `(rawLabel, shortLabel)` pair — every station-position marker producer (`station_scenario_map.dart`, `coordinator_screen.dart`, `role_mini_map.dart`'s `roleContextMarkers`) calls it instead of recomputing the numbering; it deliberately does not resolve plan-variable tokens itself, since callers need different resolution mechanisms depending on whether a `BuildContext`/ambient scope is available. `locationMarker(location, {id})` is the one shape every scenario-location pin uses (no `shortLabel` — locations don't need a zoom-tiered short form). `roleMarker` (in `role_mini_map.dart`) is now generic over the marker-id type and takes an explicit `id`, so `stations_view.dart`'s all-exercises map can reuse it instead of reimplementing role-marker construction inline — gaining the richer `resolveModelField`-based label resolution in the process. `map_picker_screen.dart`'s marker-dimming copy, found by the same audit, now forwards `shortLabel` instead of silently dropping it.

**Icon footprint independent of label visibility.** A fourth pass, found live-testing a `showLabels: false` surface (`ExerciseMiniMap`): `fitPadding` zeroed `markerHeight`/`markerHalfWidth` entirely whenever the `labels` iterable was empty — correct when there are no markers at all, wrong when markers exist but their labels are merely hidden, since the marker's *icon* still renders and is anchored the same bottom-up way a label would be. With zero reserved, the topmost marker's icon could clip right at the viewport edge — reported as "missing labels, and the top marker is just at the border." Fixed by always reserving a conservative icon-only footprint (32px height / 16px half-width at scale 1, matching the largest icon actually used, `Icons.place`) when `labels` is empty, on top of which the existing label-aware math still applies whenever labels are actually given.

**Visual centroid, not just the point centroid.** A fifth pass, from a direct observation: even with padding-bias removed, every marker is rendered `Alignment.topCenter` with its *bottom* edge pinned to its point (`_MapViewState._buildMarker`) — its icon/label box only ever extends *upward*, never symmetrically. Centring the camera on the raw arithmetic-mean point centroid therefore still leaves the rendered marker *graphics* looking shifted up: each marker's own visual centre sits half its rendered height above its point, so the group's average visual centre sits that same half-height above the point centroid. `_UnbiasedBoundsFit` gained a `markerAnchorHeight` parameter — after computing `newZoom`, it projects the centroid at that zoom, shifts it north (screen-up) by `markerAnchorHeight / 2` pixels, and unprojects back to get the final `LatLng` centre, so the correction is always computed at the fit's own real zoom rather than requiring a caller to guess one up front. `fitPadding`'s internals were split into a private `_fitPaddingAndFootprint` returning both the `EdgeInsets` and the raw per-marker footprint height, so `fitFor` can feed the same figure to both `fitPadding`'s zoom-driving padding and `centroidFit`'s new centring correction without computing it twice.

**Label detail threshold capped at the auto-fit zoom ceiling.** A sixth pass, from a live-device report that full labels (number + name, not just the short chip) only ever appeared on a compact/phone window at an unreasonably tight "10 m" scale reading, never the "25 m" reading medium/expanded windows switched at. `MapConfig.labelDetailZoomFor(sizeClass)` was defined as `labelMinZoomFor(sizeClass) + 5`, giving compact = 18, medium = 16.5, expanded = 15.5 — but `defaultAutoFitMaxZoom` (16.5, added in the second pass above) caps the zoom of *every* auto-fit regardless of size class. Compact's threshold (18) sat *above* that ceiling, so no auto-fit or "centre" tap could ever reach it — only a manual pinch past where any built-in view would land could; medium's (16.5) happened to sit exactly at the ceiling and expanded's (15.5) comfortably under it, which is why only compact showed the symptom. An initial hypothesis — that `_ZoomGatedLabel` should read `MapCamera.of(context).nonRotatedSize.width` (the local map pane) instead of `WindowSizeClass.of(context)` (the full window), on the theory this was the same local-pane-vs-full-window mismatch the self-computed-fit pass fixed elsewhere — was tried, appeared to pass under a flawed test that left the test window at flutter_test's ~800px default (medium, not the compact case under investigation), and was confirmed wrong on real devices: it made every size class collapse to the compact threshold, because `nonRotatedSize` starts at flutter_map's own `MapCamera.kImpossibleSize` placeholder before the first real layout pass and this widget kept resolving that stale value. Reverted; the actual fix is `labelDetailZoomFor(sizeClass) => math.min(labelMinZoomFor(sizeClass) + 5, defaultAutoFitMaxZoom)`, which leaves medium and expanded's thresholds unchanged (already at or under the cap) and brings compact's down to 16.5, matching medium exactly.

**Marker-count guards consolidated: `centroidFit`/`fitFor` always return a fit.** A seventh pass, from direct code-review feedback: every call into the fit machinery was preceded by its own hand-rolled marker-count guard — `centroidFit`/`fitFor`/`_defaultFitFor` returned `null` below two points, but several call sites (`MapView._toggleCenter`, `position_form_field.dart`'s `openPicker`, `stations_view.dart`'s `_recenter`/`_onStationPick`) then re-split that same `null` into their *own* separate `isEmpty`/`length == 1` branches with independently-chosen fallback values, and `stations_view.dart`'s `build()` had a third, `average()`-based ternary that silently collapsed the 1-vs-2+ distinction the other two kept separate — three different shapes for what should have been one decision. The fix follows directly from `_UnbiasedBoundsFit`'s own math: a zero-extent bounds box (0 points, 1 point, or several that coincide) already produces a scale so large that `getScaleZoom` clamps straight down to `maxZoom` — there was never a mathematical reason to special-case it. `centroidFit` now always returns a `CameraFit` (never `null`): zero points centre on a new `fallbackCenter` parameter (or `MapConfig.initialCenter`); everything else — one point, several coincident points, many spread-out points — is the same bounds-and-centroid computation. `fitFor`/`_defaultFitFor` follow suit, dropping their own guards and the now-redundant `CameraFit.coordinates` fallback that existed only for the all-coincident case. `MapView.didUpdateWidget`'s "dropped to exactly one marker" branch, `_toggleCenter`'s `isEmpty`/`length == 1` pair, `_recenter`'s `fit != null` check, and `_onStationPick`'s equivalent all collapse into a single unconditional `fitCamera` call; `stations_view.dart`'s `build()`-level `center` ternary was outright redundant with `average()`'s own empty-list fallback and is now just `markers.average()`. One genuine gap surfaced by this: the zero-marker case now legitimately reaches `_fitPaddingAndFootprint`, whose "no labels" icon-only-footprint fallback (from the fourth pass) had only ever been exercised for "markers exist but labels are hidden" — reusing it for "there are no markers at all" reserved a phantom icon footprint and applied `markerAnchorHeight`'s visual-centroid shift for an icon that doesn't exist, nudging the zero-marker default fit a fraction of a metre off `initialCenter`. Fixed with an explicit `hasMarkers` parameter (`fitFor` passes `pts.isNotEmpty`) so the icon-only fallback only fires when there is a real, unlabelled marker to protect. `_toggleCenter` and `position_form_field.dart`'s "editing an existing position" branch keep their own remaining guards deliberately — those aren't marker-count duplication, they're genuinely different operations (preserve the user's current zoom instead of fitting; don't reframe onto sibling context when a point is already placed).

### Consequences

* Good: narrow/mobile and modal-sheet/dialog map fits zoom to match the real geographic extent; the local-pane-vs-full-window `WindowSizeClass` mismatch is closed everywhere that defers to `MapView`'s own computation.
* Good: the "markers pushed toward one screen edge" bug class is closed architecturally, not just rebalanced — no future asymmetric padding source can reintroduce it, since centring no longer reads padding at all. One shared zoom constant governs "enough surrounding context" for both tight clusters and lone markers, so there's no jarring jump as a marker count crosses the 1-vs-2+ threshold.
* Good: a station's pin shows the same "number + name" everywhere, a location's pin the same shape everywhere, a role's pin the same resolved text everywhere — verified in `test/utils/map_marker_consolidation_test.dart` and a regression assertion in `station_mini_map_test.dart`.
* Good: the fitted camera now centres on where the marker *graphics* visually average out, not just the invisible anchor points beneath them — verified directly in `test/utils/marker_anchor_centering_test.dart` (zero height reproduces the old exact-centroid behaviour; a taller height shifts further north, proportionally).
* Good: every size class's full-label threshold is reachable by its own auto-fit, not just medium/expanded's — a permanent invariant test (`test/views/label_detail_zoom_reachability_test.dart`) asserts `labelDetailZoomFor(sizeClass) <= defaultAutoFitMaxZoom` for all three tiers, so this specific conflict (a zoom-tiering constant exceeding the shared auto-fit ceiling) cannot silently regress again.
* Good: zero, one or many markers are one code path everywhere in the fit machinery, not three independently-thresholded ones per call site — `centroidFit`/`fitFor` never return `null`, so a caller can no longer drift from what every other caller does for the same marker count. `test/views/map_view_single_marker_zoom_test.dart` pins the zero/one/many zoom behaviour, including that a zero-marker fit lands exactly on `initialCenter` with no phantom marker-footprint shift.
* Bad: `_UnbiasedBoundsFit` duplicates a subset of flutter_map's own `FitBounds` zoom math rather than reusing it directly — flutter_map does not expose that derivation standalone. A flutter_map upgrade that changes it would need this mirrored by hand.
* Bad: still does not cover `ProgramService.getLocations()`/`Exercise.getNumberedLocations()` (the main Stations-tab map's marker source, built at the model/service layer before any `BuildContext` exists — it still bakes the station number into its tuple directly rather than calling `stationNumbering`, and never resolves plan-variable tokens in a station's name at all) — flagged as low-priority, not required to close what was actually reported.
* Bad: `MapConfig.fitPadding`'s capping constants, `defaultAutoFitMaxZoom` and the `markerAnchorHeight` correction all use a single representative marker-footprint figure rather than each marker's own actual rendered height — a reasonable approximation given every marker in the app shares the same anchor convention and a narrow range of icon sizes, but not exact for a mixed set of very differently sized markers.
