This is showRingdrillPicker, not a new surface

The browser is one call to showRingdrillPicker<TokenBrowserEntry> (ADR-0049). The primitive already owns the chrome: a bottom sheet on compact via showRingdrillActionSheet, the rounded dialog shell on medium/expanded, a title row, a search field past a threshold, section headers computed over the filtered list, footerActions, and pop-with-the-chosen-item. None of that is redrawn here.

Row anatomy

Three lines, in the order the author asks: what is it called, what will it produce, what does it mean.

  • The left edge. The row starts where the section header starts. No leading icon: the scope is already in the header and in the token's own prefix, so an icon would push every line 30px in and take that width off the long values — in the one direction that is short.
  • Line 1 — label and token. Label first, token after it as a code chip. The label is what the author is looking for; the token is what she gets. When the line is tight the token truncates from the right, and an ellipsised token must carry a tooltip with the full string: the tail is exactly what tells {{station.person.anne.loc.position}} from {{station.person.anne.loc.name}}. Hover on desktop, long-press on touch, which Tooltip does by itself. The row's tap is insertion; its long-press is free.
  • Line 2 — the value now. What the token resolves to in this field's scope at this moment. The block wraps, so a talkgroup or a round table is readable instead of truncated — the whole reason a sheet exists. When there is nothing to resolve, an example value stands there instead, dashed and marked EXAMPLE, so the author sees the shape of what the token produces. An empty box answers nothing.
  • Line 3 — the description. For a plan field the new line in PlanFieldTokens; for a variable the hint the author wrote herself.

One filter, two presentations

The set is derived, not written. The filters are PlanFieldScope's cascade for this field (withAncestors) plus the registries the field actually has — variables always, the station's locations and persons when it owns any — in the same order as the sections. A plan-scope field gets three, a roleplay-scope field gets eight. The demand the ADR makes of the content applies to the filter too: one inventory, no second copy, so a new scope produces a new filter on its own. A scope that exists but has nothing in context stays, dimmed and still selectable — picking it shows the single row explaining why it does not apply here.

Compact: wrapping chips. Label only, no count — the count is not what an author chooses on, and it costs width where width is short. The row wraps rather than scrolling sideways: eight categories take two lines on a phone and all of them are visible, where a sideways row would hide the last few behind the edge without saying they exist.

Medium/expanded: a master rail. The same inventory laid out as the app's own wide-screen idiom (ADR-0030): scopes in the master pane, rows in the detail. That is the pattern the plan tab, the station list and the roleplay list already use on a wide window, so the browser reads as part of the app rather than as a dialog that happens to be wide. The window-size rule is the same one showRingdrillPicker already applies to the surface — one parameter, two presentations, no per-call-site choice.

Why not a segmented button? Because the app has tried it. StaffRoleFilter was a SegmentedButton until four Norwegian role names made every segment as wide as “Øvelsesleder”, overflowed a phone, and clipped the leading “Ø” when shrunk to fit; that file's doc comment is the record. Here it is worse — up to eight categories, and the set varies with context. A segmented button is also view selection in this app (the plan tab's segments, the coordinator's three views), not list filtering, and using it here would blur that.

The filters cannot live in itemBuilder either, since they would scroll away with the list. They belong in showRingdrillPicker's header as an optional filters parameter — a label and a predicate per entry — rendered as chips on compact and as a rail on medium/expanded. A picker that passes none looks exactly as it does today.

What is actually new

  • The row builder. itemBuilder belongs to the call site, so a three-line row needs no change to the primitive.
  • The descriptions. One line per facet, in both languages, beside the labels in PlanFieldTokens. Still the bulk of the work, and still why the ADR is proposed rather than accepted.
  • The example values. One per facet that has nothing to resolve in the editor — the aggregated ones, the derived ones missing their inputs, and the plainly empty ones. Same home as the descriptions; the structural ones need no translation.
  • The search text. searchText joins name, label and description. searchThreshold: 0, since the list is always long.
  • The filters parameter, the one addition to the primitive.

Without extending the primitive

  • A scope with no context is its own TokenBrowserEntry variant rendering as a muted note with no onTap. Its header comes from sectionLabel like any other row, so an empty scope is shown rather than vanishing, without the primitive learning about disabled rows.
  • The order is the cascade (plan → exercise → station → roleplay), then variables, locations, persons. sectionLabel only asks that the list is ordered by group, which it is.
  • Insertion routes through the caret menu's _select, so there is still one implementation of “what text does this entry produce”.

Panels 1 and 2 are the caret menu, which is not a picker call and does not change shape. It gains one row.
